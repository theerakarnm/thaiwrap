Full comparison

thaiwrap against the other Thai tools

We wrapped a 50 page Thai document with 7 JavaScript set-ups and 6 Rust set-ups. We measured speed, memory, install size and start-up time. We also checked that every line follows the Thai typing rules.

Apple M1 Pro (MacBookPro18,3), 8 cores, 16 GB RAM, arm64 · macOS 26.6.2 · Node v22.19.0 · measured 2026-11-01 · Full write-up: bench/RESULTS.md

Speed

1.9x or more

faster than every other JS tool, in all 9 test setups. Whole 50 pages: 12.3 ms.

Winner

Start-up

3.90 ms

to load and finish the first wrap. The others need 10.2 to 132 ms.

Winner

Peak memory

107 MB

while wrapping 50 pages 300 times. The others peak at 158 to 230 MB.

Winner

Thai line rules

0 problems

in 18,009 lines. The other tools break a rule on 0.1% to 0.6% of their lines. Only the reference wrap, which is 5.7x slower, also has none.

Winner

Install size

843 KB

download (JS plus one native binary). Pure JS tools: 112 KB to 182 KB.

Trade-off
How to read this page
  • Wrap means: cut text into lines of at most maxLength characters, and never cut a Thai word in a bad place.
  • Simple wrap is one small function we wrote and gave to every tool that only finds word boundaries, so all tools fill lines the same way. Details in Notes.
  • For time, memory and size, shorter bars are better. Each bar is the median of 3 runs. The thin line on a bar runs from the fastest to the slowest run.
  • Length is counted in UTF-16 code units, the same as JavaScript .length.

What we tested

Source: RESULTS.md, Method

The same input went to every tool. Each tool was set up once before timing, so we time the wrapping and not the set-up.

Small: ~1 page3,319 characters · 9 KB
Medium: ~10 pages28,942 characters · 81 KB
Large: 50 pages144,706 characters · 405 KB

The text mixes Thai prose, Thai digits, English words, numbers, punctuation and emoji. It also holds zero width spaces and no-break spaces, which real documents contain. Each test used three line lengths: 20, 40 and 80.

ToolVersionKindWhat it is
thaiwrap ours0.1.1oursWraps by itself: ICU4X dictionary + Thai line rules.
Intl.Segmenter + Thai rulesNode v22.19.0baselineThe reference wrap used in the tests. Built in, no install.
Intl.Segmenter + simple wrapNode v22.19.0baselineBuilt-in word finder plus the shared simple wrap.
wordcut0.9.1npmThe classic JS word breaker. Needs an init() call to load its dictionary.
thai-wordcut-ts1.0.2npmMaintained fork of wordcut.
thai-break1.5.0npmNewest. Measured two ways: words() plus simple wrap, and its own wrap().
ICU4X (icu_segmenter)2.4.0RustThe word finder inside thaiwrap, without our Thai rules.
wordcut-engine1.2.2RustThe library behind chamkho 1.5.0, used with chamkho's own dictionary.
nlpo31.4.0RustPyThaiNLP newmm engine in Rust.
thaibreak1.5.0RustSame engine as the thai-break npm package.
kham-core0.8.2RustSmall pure Rust segmenter.

Not in the speed charts: the nlpo3 npm package. It has no prebuilt binary and fails to install without a Rust toolchain, so the Rust crate is tested instead. See Notes.

Where thaiwrap wins, and where it does not

Source: RESULTS.md, Wins / losses summary

Wins

  • Fastest in all 9 JS setups. On the full document it is 1.9x to 33x faster than the other tools.
  • Within 10% of raw ICU4X in every setup (the Thai rules are almost free), and 2.3x to 3.1x faster than the other Rust crates.
  • Smallest start-up (3.90 ms) and lowest peak memory (107 MB).
  • No Thai rule problems in 18,009 lines, and no line longer than the limit.
  • Cuts overlong words at safe places and has options for how to measure length.

Trade-offs

  • A native binary: 843 KB to download, and not usable in a browser.
  • ICU4X splits compounds more finely than PyThaiNLP newmm. If you need newmm compatible word boundaries, it differs.
  • About 2.78 ms per 50 pages goes to moving strings between JS and Rust.
  • One machine, three runs each. Numbers will differ on your hardware, ratios should not.

Notes and fairness

Source: RESULTS.md, Notes and exclusions
The shared simple wrap

Tools that only find words use one greedy function: fill each line with as many words as fit, never cut a word, keep a space only where the input had one, drop zero width spaces, keep blank lines between paragraphs. Length is in UTF-16 units. It has no rule for ะ า ำ ๆ ฯ or leading vowels. That is what the Quality table measures. A no-break space is treated like a normal space by this function.

Why nlpo3 on npm is not in the speed charts

npm i nlpo3 runs cargo-cp-artifact, which is not installed, and would need a Rust toolchain anyway. There is no prebuilt binary. The Rust crate is tested in the Rust charts.

chamkho and its license

chamkho 1.5.0 ships only a command line program. The test links its engine, wordcut-engine, with chamkho's own dictionary. wordcut-engine is LGPL-2.1, so deny.toml has a narrow exception for it. It is only used by the benchmark crate, never by thaiwrap.

thai-break and the unit of width

thai-break counts display columns and treats tone and vowel marks as zero wide. The same number means a longer line than in thaiwrap, which counts UTF-16 units. Both are valid choices.

Measurement details

JS speed: 3 rounds, each in a fresh Node process; the value shown is the median of the 3 round means and the thin line is the fastest to slowest round. Rust speed: 3 criterion runs (warm-up 500 ms, 2 s of measurement, 50 samples); the value shown is the median of the 3 median estimates. The machine was not idle: macOS system services used CPU during the runs, which is why the range is shown. Start-up: median of 15 fresh processes. Memory: one process per tool, 300 wraps. Reference word breaks: PyThaiNLP 5.4.0 newmm. Single machine, not guaranteed idle.
