# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor and similar) working in this repository. Humans should read [README.md](README.md) first.

## Project overview

`thaiwrap` wraps Thai text into lines of a maximum length at word boundaries. It is written in Rust and published to npm as a Node-API addon built with [napi-rs](https://napi.rs), targeting Node.js 18+ and Bun.

Core behavior, which every change must preserve:

```js
wrapThai("กระบวนการสื่อสาร ส่งมอบ และสร้างคุณค่า", 10)
// ["กระบวนการ", "สื่อสาร", "ส่งมอบ และ", "สร้าง", "คุณค่า"]
```

This is the **acceptance test**. If a change breaks it, the change is wrong.

Status: pre-release (v0.x). The public API may still change, but only through an explicit decision recorded in the PR description.

## Repository layout

```
crates/
  thaiwrap-core/     Pure Rust: segmentation + wrapping. No napi, no JS types.
  thaiwrap-node/     Thin napi-rs binding. Converts JS <-> Rust, validates input, maps errors.
npm/                 Per-platform npm packages generated by napi-rs
__test__/            JS tests (bun test), run against the built addon
benches/             criterion benchmarks for the core crate
bench/               JS benchmarks (Node and Bun)
index.js, index.d.ts Generated by napi-rs. Do not edit by hand.
```

Keep all logic in `thaiwrap-core`. The binding crate only converts types, validates arguments and maps errors. If you find yourself writing wrapping logic in `thaiwrap-node`, move it to the core.

## Rust best practices

### Toolchain and crate settings

- Use the stable toolchain pinned in `rust-toolchain.toml`. Do not use nightly features.
- Edition 2021. Respect the MSRV declared in `Cargo.toml` (`rust-version`); do not use newer std APIs without bumping it in a separate, explicit change.
- Commit `Cargo.lock`.
- `thaiwrap-core` starts with:

  ```rust
  #![forbid(unsafe_code)]
  #![deny(missing_docs)]
  #![warn(clippy::pedantic)]
  ```

  Allow individual pedantic lints locally with `#[allow(clippy::...)]` and a one-line comment saying why. Never blanket-allow at crate level.

### Safety and panics

- **No `unsafe`** anywhere in v0.x. If you believe it is needed, stop and ask.
- **Never panic across the FFI boundary.** A panic inside a napi function can take down the user's process.
- No `unwrap()`, `expect()`, `panic!`, `unreachable!` or indexing that can go out of bounds in library code. Tests and benches may use `unwrap()`.
- Slice strings only at boundaries returned by the segmenter or by `char_indices()`. Never slice `&str` at arbitrary byte offsets; Thai characters are 3 bytes in UTF-8.
- Use checked or saturating arithmetic for anything derived from user input (lengths, offsets).

### Errors

- The core returns `Result<T, WrapError>`, where `WrapError` is an enum with one variant per failure (for example `InvalidMaxLength`).
- Implement `std::error::Error` and `Display` by hand. Do not add `thiserror` or `anyhow` to the core; keep it dependency-light.
- The binding maps errors to JS: invalid types become `TypeError`, invalid values become `RangeError`. Error messages are written for JS users, not Rust users.

### API design

- Take `&str`, return owned `Vec<String>` only at the binding layer. Inside the core, prefer returning byte ranges (`Vec<Range<usize>>`) or iterators so callers can avoid allocations.
- Use a `WrapOptions` struct with `Default` for options. Do not add positional boolean parameters.
- Mark public enums and option structs `#[non_exhaustive]` so new options are not breaking changes.
- Every public item has a doc comment with at least one example that compiles as a doctest.

### Performance

- Build the ICU4X segmenter once and cache it in a `std::sync::OnceLock`. Never construct it per call.
- Avoid allocating per segment. Track line length as a counter instead of re-measuring the accumulated string.
- Do not add `rayon`, threads or async. Wrapping one string is a few microseconds; parallelism costs more than it saves.
- Any change that claims to be faster must include `cargo bench` numbers before and after in the PR description. Do not merge regressions over 5% without discussion.
- Release profile stays: `lto = true`, `codegen-units = 1`, `strip = true`, `opt-level = 3`.

### Dependencies

- Allowed in the core: `icu_segmenter` and the ICU4X crates it needs. Nothing else without approval.
- Allowed in the binding: `napi`, `napi-derive`, `napi-build`.
- Dev-dependencies (`criterion`, `proptest`) are fine.
- Before adding any dependency, stop and ask. Explain what it does, its size, and why std or the existing crates are not enough.

### Style

- `rustfmt` defaults. Do not commit a custom `rustfmt.toml` without approval.
- Small functions with descriptive names. Prefer iterators and `match` over index loops and long `if` chains.
- Comments explain *why*, not *what*. Thai-specific rules always get a comment with an example, because most readers cannot read Thai.

## Thai text rules

These are correctness rules, not style preferences. Tests must cover each one.

1. **Never start a line with a combining mark** (vowels above or below, tone marks, for example `ั ิ ี ึ ื ุ ู ่ ้ ๊ ๋ ็ ์`).
2. **Never end a line with a leading vowel** (`เ แ โ ใ ไ`). They belong to the consonant after them.
3. **Never start a line with** `ะ า ำ ๆ ฯ`.
4. **Length is measured in UTF-16 code units by default** (same as JS `.length`). This is what makes the acceptance test pass. Other measures must be opt-in through options.
5. **Whitespace at line edges is trimmed.** Spaces are break opportunities, not content.
6. **A word longer than `maxLength`** is handled by the documented overflow strategy, never by slicing at an arbitrary position.

## Testing

- **Unit tests** live next to the code in `#[cfg(test)] mod tests`.
- **The acceptance test** exists in both `cargo test` and `bun test`. Never delete or weaken it.
- **Property tests** (`proptest`) on random Thai and mixed strings must check:
  - no line violates the Thai text rules above;
  - every line fits `maxLength`, except a single overflow word when the overflow strategy allows it;
  - joining the lines and removing whitespace gives the input with whitespace removed (no text is lost or duplicated).
- **Segmentation outputs:** never hard-code an expected result you have not observed by running the code. If you are unsure how ICU4X segments a string, run it first, then write the assertion.
- **JS tests** must pass on both Node and Bun.
- Bug fixes start with a failing test that reproduces the bug.

## The napi binding

- Exported names follow JS conventions (`wrapThai`, `maxLength`). napi-rs converts `snake_case` automatically; check the generated `index.d.ts`.
- Validate every argument at the boundary before calling the core: `maxLength` must be a finite positive integer.
- Do not edit `index.js` or `index.d.ts` by hand; regenerate them with `bun run build`.
- Keep the exported surface small. Every new export is a public API decision.

## Commits and pull requests

- Conventional Commits: `feat:`, `fix:`, `perf:`, `test:`, `docs:`, `refactor:`, `chore:`, `ci:`.
- One logical change per commit. Do not mix refactors with behavior changes.
- PR descriptions include: what changed, why, how it was tested, and benchmark numbers for anything touching the core loop.
- Update `README.md` when public behavior or options change.

## Stop and ask before

- Adding, removing or upgrading a dependency
- Changing the public JS or Rust API, defaults, or the acceptance test
- Writing any `unsafe` code
- Changing the platform build matrix, CI release workflow or npm publish settings
- Changing the ICU4X data source (compiled data vs custom datagen), since it can change segmentation output
- Deleting files or tests

## Never

- Commit secrets, npm tokens or `.npmrc` files with credentials
- Run `npm publish` or create release tags
- Skip or ignore failing tests to make CI green
- Guess segmenter output in tests or docs
